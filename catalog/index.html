문제에서 결과까지

문제

요청 실패와 작업자 중단이 유실·중복으로 이어지고, 사이트 구조가 바뀌면 잘못 파싱한 데이터를 정상 값으로 저장할 수 있습니다.

선택

저장과 작업 등록을 트랜잭션으로 묶고, 중단 메시지 회수와 멱등 저장을 적용했습니다. 문서 구조 지문과 필드 품질이 달라지면 검수 대상으로 분리했습니다.

결과·활용

통제 환경에서 복구와 무결성을 확인하고 공개 연습용 사이트 20개 상품을 수집했습니다. 브라우저 파싱 체험과 실제 실행 기록을 공개했습니다.

구현 과정과 선택 이유

  1. 저장·등록 일관성

    대상 데이터와 outbox를 동일 트랜잭션에 저장하고 Redis Streams로 작업자에게 전달했습니다.

  2. 중단·일시 오류 복구

    Retry-After와 지수 backoff, 회로 차단, stale message 회수와 멱등 저장을 적용했습니다.

  3. 문서 구조 변경 감지

    JSON-LD·선택자·메타데이터 순서로 파싱하고 필드 품질과 DOM 지문 변화로 검수 여부를 판단했습니다.

  4. 근거를 공개

    소스·테스트·실행 JSON과 파싱 체험을 연결해 입력부터 저장 결과까지 확인할 수 있도록 했습니다.

검증 근거

  • 공개 복구 훈련 기록: 1,000개 대상 성공, 일시 오류 83건을 포함한 1,083회 요청, 중단 작업 17개 회수, target_id 기준 유실·중복 0건.
  • 필수 필드 400/400 정확, 공개 연습용 사이트 연결 20/20 성공은 각각 별도 검증입니다.
  • 10ms 지연을 고정한 1,000페이지 통제 실험의 처리량은 단일 처리 대비 28.76배였습니다. 실제 쇼핑몰 처리량으로 확대하지 않습니다.
